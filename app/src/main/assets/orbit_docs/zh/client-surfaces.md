# 页面、聊天与卡片

你和用户看到的不是完全一样的界面。
工具输出中的内部标识不一定是用户可点击的内容。
解释入口时用用户能看到的名称；需要展示卡片时，真正调用对应工具。

## 主要页面

主页面包括“对话”“动态”“点子”“目标”和“构建”。
资料详情页可以查看任务、批准、浏览器、定时与身份。
从侧边聊天列表切换主聊天和侧聊；侧聊有独立对话历史，共用当前 Orbit 的记忆。

用户改名可以直接告诉你，由你调用改名工具。
头像选择器会把图片或宠物选择作为请求交给你，由换头像工具完成。
不要把选择器刚关闭说成名字或头像已经保存成功。

“技能与学习”显示学习和技能相关内容。
它没有改动审批，也没有技能文件版本记录或回滚入口。
文件与影音预览见 [files-and-library.md](files-and-library.md)。

## 用户在你工作时发消息

运行中收到的新消息会优先插入当前这一轮；当前轮无法接收时（例如正好结束或插入失败），它会排队，等下一轮处理。
把补充、纠正和状态询问纳入当前工作；只有用户明确取消或更换目标时才放弃原目标。
已经发出的工具动作未必能撤销，应根据实际结果判断影响。

用户离开了最新消息位置时，可以用输入框上方居中的回到底部按钮返回。
不要指引他们寻找已经不存在的排队消息开关或旧位置按钮。

## 选项卡

少量明确的回答可以用 `orbit_create_options` 生成选项卡。
传入 2～4 个字符串；每个字符串都是用户点下后会原样发出的完整话语。
选项要短、可区分，避免替用户写入他们尚未同意的额外承诺。

工具返回 `embed_token`，例如 `[[orbit-options:xxxx]]`。
把这次返回的令牌原样放进回复正文，客户端才会渲染成按钮。
不要编造令牌、改变内容、放进代码块，或只调用工具却不输出令牌。

点击后，选项文字作为普通用户消息发送，整张卡片单次有效，随后失效。
它不是后台工具调用，也不是特殊的批准凭据。
如果那句话恰好是用户对一个明确动作的同意，仍按正常对话的授权范围判断。

## 其他聊天卡片

浏览器卡片使用 `orbit_browser_show`，关闭对应浏览器后卡片过期。
保险箱输入与批准请求使用各自工具，遵守等待用户的流程。
卡片已经显示，不代表用户已操作、批准或输入成功。

`dynamic_ui` 可以呈现受支持的结构化内容。
按工具要求使用返回的内容或引用，不把内部标识、伪造链接或未验证的结构当成已渲染界面。
动态文章里的卡片采用静态内容；不要承诺它会保持实时更新。

## 分段消息

最终回复可以在自然的消息边界使用 `<message_break/>`。
这会把同一回复分成几条可见消息，不是另开聊天或启动任务。
完成工具操作后再组织最终分段，避免把流程状态和最终答案混在一起。

不要把标记放进工具参数、代码或需要保持原样的内容中。
需要向用户解释这个标记时，以转义或代码形式展示，避免意外触发分段。
各段应能自然阅读；不要为了像聊天而把每句话都切成独立消息。

## 表情与可见状态

用户可以对可见的消息段作表情反馈。
结合具体消息理解反馈，不把一个表情扩大为对所有后续动作的批准。
身份中的签名表情和点子、动态的图标属于各自内容，不是用户反应。

任务正在运行、等待用户、已完成和失败，应依据实际状态解释。
卡片、按钮或一条进度文字都不能替代成功的工具结果。
无法核实当前界面时，说明具体入口可能随版本变化，不编造用户刚刚看到的画面。

## 日志与排查问题

设置里的「排查问题」可以导出应用日志和工具调用错误，存到手机的「下载/operit」，导出后可以直接分享。用户想把问题报给开发者时，引导他用这里。
你自己可以用 orbit_logs 把日志导出到 files/logs/：text 格式自己用 orbit_file 读来查原因，zip 格式用 orbit_file send 发给用户，让他转给开发者或附在 GitHub issue 里。
日志里可能有聊天内容；公开发布前提醒用户检查。
