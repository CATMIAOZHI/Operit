# 行程规划

## 什么时候用

- 用户需要决定日期、路线、住宿地点或多天安排时使用。已有行程中的签证、入境、中转和机场衔接问题，也留在这里处理。
- 只是订一张已确定路线的票、一个酒店或一段交通时，直接加载对应技能。缺一个订票信息，不等于要重做整趟旅行。
- 已经在规划中的一部分，继续遵守用户的顺序。用户说先排完整行程，就不要把查价格变成催促下单。

## 按需读参考

加载本技能时返回的 **Skill directory** 就是本技能目录。用当前可用的读文件工具读取该目录下的文件，不猜设备绝对路径，也不把相对链接当成已经读过。

| 什么时候读 | 文件 |
|---|---|
| 开始有多个决定的旅行，整理背景、日期和偏好前 | `references/planning-kickoff.md` |
| 日期、机场、中转或城市顺序未定时 | `references/flight-itinerary-discovery.md` |
| 排多天日程、修改计划、整理待办或交付行程文件前 | `references/operational-itinerary.md` |
| 建议签证、入境、中转、机场流程或接送衔接前 | `references/travel-fact-verification.md` |
| 把行程中的一项交给预订技能查实时报价或开始预订前 | `references/booking-handoff.md` |

## 先把旅行安排清楚

- 先看用户已经说过的要求、相关行程文件和确认信息。弄清目的、日期及弹性、同行人、预算和节奏，只追问最影响方案的缺口。
- 选日期时，在任务范围内查手机日历，覆盖整个候选时段，包括全天和出行日程。先加载 `scheduling` 技能，按 `orbit_device` 实际支持的命令读取。用户给了准确日期就保留，有冲突提醒一次；没读到日历不能说有空，也不能由一个人的日历推断其他人有空。
- 每趟旅行只维护一份当前计划。已确认的预订默认固定；用户口述但未独立核实的预订也保留，并标清来源。不要擅自改订、重复预订或把它降成候选。
- 所有时间按事情发生地写清，跨日到达要写实际日期。用高德、百度地图或目的地可靠地图查地点和门到门路线；不要凭直觉填路程或中转时间。
- 比较整趟旅行的费用和时间。便宜机票可能多花一晚住宿；可在允许范围内比较高铁、不同城市进出、少换酒店等方案。给重要活动准备天气或闭馆备选。
- 营业日、预约、末班车和出入境要求用负责该事实的官方来源核实，注明链接和核查日期。小红书、游记和点评适合找灵感，不能证明现行规则。

## 把预订交给对应技能

用 `orbit_skills` 找技能，再按返回的真实 `package_name` 用 `use_package` 加载，不猜工具包名。

- 订机票时加载 `flight-booking` 技能。
- 订酒店或民宿时加载 `hotel-booking` 技能。
- 火车、租车、轮渡、巴士或接送加载 `trip-transport` 技能；国内铁路实时信息以 12306 为准。
- 安排日历或提醒时加载 `scheduling` 技能。
- 景点和活动先查主办方官网，再比较携程、飞猪、美团等合适平台。只有用户要求预订才进入提交步骤。

把已选路线、日期、人数、预算、限制和来源一并带过去；结果写回原计划。价格查询不等于预订授权，页面有票也不等于订单确认。

需要用户输密码、验证码、过人机验证或付款时，用 `orbit_browser_handoff` 交还浏览器，结束本轮等待。用户交回后重新看页面；付款结果不明先查订单，不重复提交。Orbit 不能替用户付款。

## 保存和交付

- 用 `orbit_file` 在 `files/` 下保存该旅行的行程，继续时先读当前文件再改。不同旅行各用自己的记录，不拿临时目的地覆盖长期住址或偏好。
- 具体承诺可用 `orbit_tracking` 跟进；它不会自动检查变化。需要以后提醒或查变化时，先读 `docs/scheduling-and-watching.md`，再按用户要求创建 `orbit_task`，检查实际时区和下一次运行时间。
- 照片和地图只在有帮助、来源可核实时使用；没有可靠图片就省略。交付文件要用 `orbit_file action=send`，不能只报路径。有未解决的重要事项，就说清下一步。
