### R24：损坏的远程 MCP 参数拦截

- 上游提交：`17df7f9e9`
- 审查结论：`ADAPT`
- 实施状态：已完成来源复核；暂不实施无来源拦截

当前执行路径已经证明：`AIToolHandler` 会在执行前调用 `MCPToolExecutor.validateParameters`；随后 `MCPToolExecutor` 把 `AITool.parameters` 转成 MCP 参数并调用远端 session。因此若能证明参数已经因 UTF-8 解码错误损坏，这里确实是阻止远端写入的最后安全边界。

但上游补丁仅根据参数字符串中出现 U+FFFD 拒绝调用。U+FFFD 本身是合法 Unicode 字符，当前 `AITool` 只保存字符串，没有“此字符由解码器替换非法字节而来”的 provenance。上游 issue 记录证明服务端收到过 U+FFFD，却没有在本仓库中提供原始响应字节或严格解码失败证据；当前个人版也包含多 provider、多种流式工具参数拼装路径，不能从最终字符串反推来源。

因此本轮不照搬全局 U+FFFD 拦截，避免把用户有意提交的替换字符误判为损坏并阻断远程 MCP。可实施条件是：在 provider/SSE/工具参数组装边界使用严格 UTF-8 解码或传播明确的 decode-integrity 标记，再让 MCP 验证只拒绝带有损坏 provenance 的参数；在此之前保持台账项未完成，不声称已修复 issue 858。
